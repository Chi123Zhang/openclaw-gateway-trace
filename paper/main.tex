\title{TraceClaw: Source-Anchored Auditing of the\\
LLM Agent Control Plane}

\author{Anonymous Author(s)}

\date{August 2026}

\begin{document}

\maketitle

\begin{abstract}
Most agent papers evaluate what an agent answers. Much less attention is
given to the control plane that decides whether a request is accepted,
which agent receives it, whether work is admitted, and where control
passes from gateway code into the deeper runtime. This gap matters because
many safety, reliability, and reproducibility claims depend on decisions
made before model generation starts.

This paper introduces TraceClaw, a source-anchored ledger for auditing
LLM agent control planes. Distributed traces can say what executed, and
source code can say what may execute, but neither by itself explains why a
specific branch was selected or which nearby branches were not taken.
TraceClaw writes each control-plane stage as a falsifiable claim: the
claim has source anchors, concrete request values, an observation status,
and the branch decision. We apply the method to the OpenClaw Control
UI/WebChat \texttt{chat.send} path for the Cake2 request,
\texttt{How to make a cake?}. The ledger covers all 19 Gateway stages
(\(\mathrm{cov}=19/19\)); 16 of those stages have direct runtime or native
stage-outcome observation, while G6, G15, and G16 require
source-grounded reconstruction. We then audit six separately saved New
York weather
traces from repository history. These traces preserve the same G0--G18
control-plane structure and record a tool-using post-G18 path through
\texttt{web\_search}, \texttt{agent\_reply\_finalized}, and
\texttt{reply\_resolver\_returned}; two of the six also record a
\texttt{bash} skill-loading probe before \texttt{web\_search}. The
evaluation is small and same-configuration, but it shows how hidden agent
infrastructure behavior can be turned into a checkable evidence ledger
rather than a loose narrative.
\end{abstract}

\section{Introduction}
\label{sec:introduction}

LLM agents are increasingly deployed as runtime systems rather than as
single model calls. A user message may look simple in the interface, but
the system must first decide whether the connection is trusted, whether
the method is allowed, whether the payload is valid, which Session owns
the work, which Agent should handle it, whether an existing run blocks the
new one, and which resolver should produce the reply. These decisions are
not background plumbing. They form the control plane of the agent system.

The problem is that this control plane is hard to audit after the fact.
Product logs often show that a reply was generated, but not why the
request was allowed. Architecture diagrams show components, but not the
branch a concrete request took. Source code contains the rules, but source
alone gives possible paths rather than the path that actually happened.
This paper argues for a middle layer: a compact trace that is readable in
the paper, yet precise enough to be checked against source and runtime
evidence.

We study this problem through OpenClaw v2026.7.1-2, commit
\seqsplit{0790d9f593ad30c940ed93b5872a8cf6d6f3cf8c}. The case is the
Control UI/WebChat \texttt{chat.send} path for the Cake2 request,
\texttt{How to make a cake?}. The case is intentionally small. Its value
is that the whole gateway path can be reconstructed end to end, including
where the request crosses from Gateway control logic into deeper reply
runtime work, and how the result returns to Gateway control flow.
We use existing OpenClaw architecture notes as orientation, especially for
the control-plane, session, event-loop, and observability concepts
\cite{openclawPart1,openclawPart6,openclawExplained}. The stage labels and
source ranges in this paper are then re-derived from the pinned OpenClaw
source snapshot, not copied from those overview articles.

The motivation is not that Cake2 is a special benchmark. It is the
opposite: an ordinary request is enough to reveal a missing audit
primitive. If we cannot explain how one message becomes accepted runtime
work, then stronger claims about agent safety, routing, provenance, or
reproducibility rest on a fragile base.

TraceClaw treats control-plane auditing as an alignment problem between
three imperfect evidence sources. Logs give facts about one run, but can
miss silent branches. Source code gives the rules, but includes paths that
were not taken. Architecture diagrams give orientation, but erase
case-specific decisions. The proposed trace binds these sources together:
it records the value that selected a branch, the source range that defines
the branch, the runtime event that supports it when available, and the
point where evidence becomes indirect. This is the paper's central
theme: an agent request should be auditable as a chain of source-grounded,
case-specific claims.

\section{Research Questions and Contributions}
\label{sec:questions-contributions}

The study is guided by three research questions. They are phrased around
the control-plane audit problem, not around answer quality.

\begin{enumerate}
    \item \textbf{RQ1: Executed control path.} Which concrete gateway
    path turns a user-visible message into accepted runtime work?

    \item \textbf{RQ2: Source-runtime alignment.} Which source branches,
    request values, and runtime events are needed to justify each step of
    that path?

    \item \textbf{RQ3: Boundary closure.} Where does Gateway processing
    hand control to the deeper Agent Runtime, and how can the returned
    result be linked back to Gateway post-processing?
\end{enumerate}

The paper makes three contributions, each tied to a checkable result.

\begin{enumerate}
    \item \textbf{Control-plane audit framing.} We treat authentication,
    routing, admission, duplicate-run checks, and resolver selection as
    first-class audit targets, rather than evaluating only the final model
    output.

    \item \textbf{Source-anchored evidence ledger.} We propose a trace
    representation in which each stage is a small claim backed by source
    anchors, case values, observation status, negative evidence, and a
    branch decision. On the Cake2 case, the ledger explains all 19 Gateway
    stages while showing that direct runtime/native stage-outcome
    observation covers 16 of them.

    \item \textbf{Boundary-return accounting.} We show that a gateway
    trace should not stop at resolver selection. The Cake2 case maps
    G0--G18 and the G18 boundary; six separately saved weather traces
    show the tool-using post-G18 path and the resolver return edge back to
    G16/G14.
\end{enumerate}

\subsection*{Why This Is Nontrivial}

Gateway tracing is difficult because the gateway is neither a single
request handler nor a clean model pipeline. One accepted message touches
connection state, permission checks, message normalization, Session
metadata, Agent lookup, lifecycle admission, and a resolver boundary. Some
of these decisions emit runtime events; others leave only source-level
evidence. The method is therefore designed to be honest about mixed
evidence. It does not pretend that every stage is equally observed.
Instead, it marks what was observed, what was derived from source, and
where additional instrumentation would make the claim stronger.

\section{Related Work}
\label{sec:related-work}

\textbf{Agent-system architecture.}
OpenClaw architecture notes describe the broad control plane, sessions,
event loop, Gateway, and Agent Runtime design
\cite{openclawPart1,openclawExplained}. The reliability and observability
discussion further argues that production agent systems need durable
evidence, not only final outputs \cite{openclawPart6}. These sources are
useful orientation for the system studied here. Our analysis differs in
scope and evidence level: instead of restating the architecture, we pin
the primary OpenClaw source snapshot and reconstruct the actual source
path taken by a primary request, then separately audit a small set of
saved tool-using traces.

\textbf{Distributed tracing and provenance.}
Systems such as Dapper and OpenTelemetry make distributed execution
visible through traces and spans \cite{dapper2010,opentelemetryTrace}.
Provenance models such as W3C PROV provide a general vocabulary for
recording how entities and activities are related \cite{provDM}. These
ideas are close to TraceClaw, but the unit of explanation is different.
Distributed tracing records what executed. Provenance records where data
or artifacts came from. TraceClaw records why a control-plane branch was
taken for a concrete request: which value selected it, which adjacent
branches were not selected, and whether the decision was directly logged
or only source-derived.

\textbf{Dynamic analysis and slicing.}
Program slicing and dynamic slicing reduce a program to statements
relevant to a value or execution \cite{weiser1984,agrawalHorgan1990}.
Dynamic invariant detection, exemplified by Daikon, observes executions
and reports likely properties of computed values \cite{daikon2007}.
TraceClaw borrows the spirit of execution-specific analysis, but it does
not try to compute a minimal slice or infer invariants automatically. Its
output is an audit ledger for agent infrastructure: a stage-by-stage
record of branch claims, values, source anchors, direct observations, and
missing observations.

\textbf{Debugging and visual analytics for agents.}
Recent work on agent debugging and visual analytics shows that process
structure matters when final answers are not enough. XAgen studies
explainability and failure correction in multi-agent workflows
\cite{xagen2026}. Illuminating LLM Coding Agents analyzes coding-agent
behavior across code, process, and model levels
\cite{wang2025illuminating}. FlowForge uses interactive visualization as
a scaffold for designing multi-agent workflows \cite{hao2025flowforge}.
These systems motivate trace views that expose execution structure. Our
focus is lower in the stack: we trace the Gateway decisions that happen
before the deeper agent loop is allowed to run.

\textbf{Runtime observability and security.}
Runtime-observability systems such as Fangcun Observer emphasize evidence
about commands, file activity, network access, and behavior chains
\cite{fangcunObserver}. TraceClaw is closer to this line of work than to a
model-output benchmark: it treats source branches, runtime events, and
concrete request values as audit evidence \cite{traceclawArtifact}. The
main difference is the boundary being studied. We ask how an accepted
request crosses from Gateway control logic into the Agent Runtime and how
the resolver result returns to Gateway post-processing.

\section{Method: Source-Anchored Runtime Trace}
\label{sec:method}

TraceClaw is a source-anchored auditing method for agent control planes.
It is meant for systems that are too large to print line by line, but
where a claim about execution still needs concrete evidence. The method
has four steps.

\begin{enumerate}
    \item \textbf{Choose an audited request family.} Keep one primary
    request for the full source audit, then add repeated comparison runs
    when saved traces are available. Preserve the request values that
    determine control flow, such as Session key, Session ID, message,
    Agent ID, and run ID.

    \item \textbf{Trace the source path in execution order.} Follow the
    path from WebSocket connection handling to reply-resolver selection.

    \item \textbf{Attach runtime evidence.} Add observed events, values,
    and timing information where the trace exposes them. When a branch is
    source-derived rather than directly logged, mark it as such.

    \item \textbf{Separate explanation from evidence.} Keep the main text
    readable, and move exact source locations, long traces, and settings
    to the appendix.
\end{enumerate}

The main design choice is claim-level tracing. The trace is not a prose
story written after the run; it is a set of small claims. Each stage
answers four questions: which code can execute this step, which concrete
value selects the branch, which runtime evidence supports the claim, and
what would contradict it. The last question is important. Negative
evidence, such as the absence of a duplicate run or the absence of an
Agent-specific override, often explains why the accepted path was taken.
Recording this negative evidence makes the trace useful for audit and
debugging. If a later run takes a different branch, the difference should
appear as a changed value, a changed source range, or a missing event,
rather than as an informal disagreement about the architecture.

For analysis, the Gateway path is decomposed into nineteen stages,
G0--G18. These labels are introduced by this paper; they are not native
OpenClaw stage names. They make it possible to refer to a stable step
without copying hundreds of lines of source into the main text. The
numbered Gateway model stops at G18 on purpose. Events after G18 are
kept in a separate Agent Runtime layer, following the TraceClaw artifact
design \cite{traceclawArtifact}, rather than being renamed into a synthetic
G19.

\subsection*{Trace Model}

Let one user request be
\[
    r=(m,k,u,a,c),
\]
where \(m\) is the message text, \(k\) is the Session key, \(u\) is the
run identifier, \(a\) is the resolved Agent, and \(c\) is the channel or
client context. A source-anchored trace is modeled as
\[
    \tau(r)=\langle S,A,E,\rho\rangle .
\]
Here \(S=\langle s_0,\ldots,s_{18}\rangle\) is the ordered Gateway stage
sequence, \(A=\langle a_0,\ldots,a_6\rangle\) is the post-G18 Agent
Runtime event sequence, \(E=\{E_i\}_{i=0}^{18}\) is the evidence ledger,
and \(\rho\) is the return edge from the deeper runtime back to Gateway
post-processing.

For each Gateway stage \(s_i\), the evidence item is
\[
    E_i=(C_i,V_i,O_i,B_i),
\]
where \(C_i\) is the set of source-code anchors, \(V_i\) is the set of
case values used by that stage, \(O_i\in\{\mathrm{Observed},
\mathrm{SourceDerived},\mathrm{NotObserved}\}\) is the evidence status,
and \(B_i\) is the branch decision supported by the source and runtime
data. The method is useful only if most stages have both source anchors
and case values. We therefore report coverage as
\[
    \mathrm{cov}(\tau)=
    \frac{1}{19}\sum_{i=0}^{18}
    \mathbb{1}\!\left[C_i\neq\varnothing \wedge V_i\neq\varnothing\right],
\]
and direct observation support as
\[
    \mathrm{obs}(\tau)=
    \frac{1}{19}\sum_{i=0}^{18}
    \mathbb{1}\!\left[O_i=\mathrm{Observed}\right].
\]
The first score asks whether the stage is auditable; the second asks
whether the stage outcome is directly emitted by the runtime. The second
score is deliberately narrow. It does not mean that every internal
predicate, intermediate value, returned field, or rationale for that
outcome is also emitted. Thus a run can have
\(\mathrm{obs}=19/19\) at the stage-outcome level and still expose
rationale-level observability gaps inside G10, G14, G16, or G18. This
distinction is central: a stage can be source-grounded and still not have
a standalone runtime event, and an observed stage can still hide the
predicate that made the branch succeed. In practice, this lets the paper
avoid a common trap in agent observability: equating ``not logged'' with
``not explainable.''

This model gives the method a clear failure mode. A trace is weak if many
stages have source anchors but no case values, because it may describe a
possible path rather than the executed path. It is also weak if runtime
events are present but cannot be mapped back to code, because the evidence
then explains that something happened without explaining why it happened.
The strongest evidence is the intersection of source anchor, concrete
value, runtime event, and branch decision.

\section{Framework}
\label{sec:framework}

Figure~\ref{fig:paper-framework} is the central framework of the paper.
It shows the paper's argument in one view. A concrete request enters the
gateway. The gateway is reconstructed as four ordered stage groups. Each
stage is checked against an evidence ledger. The trace then supports
three auditable claims: the request was accepted, routed, and handed to
the deeper runtime at a clear boundary.

The framework is intentionally modest. It does not try to summarize the
whole OpenClaw system, and it does not claim that one trace explains every
possible request. Its contribution is a disciplined unit of analysis for
agent infrastructure: one pinned source snapshot, one ordered trace per
run, and one explicit evidence ledger. The same unit can be repeated for
other requests, compared across versions, or used to decide where more
logging is needed.

\subsection*{Run Narrative}

The run has three parts. First, G0--G2 decide whether the WebSocket
connection can be trusted. The shared-token attempt does not accept the
connection by itself, but a device-token candidate is present, and G2
accepts that path. Second, G3--G13 decide whether this particular
\texttt{chat.send} call is allowed to become work. The gateway validates
the request, loads the Session, resolves Agent \texttt{main}, checks that
the run is new, and builds the message context. Third, G14--G18 move the
accepted request into reply dispatch. G18 selects
\texttt{getReplyFromConfig}. That is the practical boundary between
Gateway-side control logic and the deeper reply / Agent runtime.

\section{Experiments and Evidence}
\label{sec:experiments}

The evaluation is a trace-validation study, not a model-quality
benchmark. We are not asking whether an answer is good; we are asking
whether the path that produced it can be checked against source code and
runtime values. The evidence is split deliberately. Cake2 is the Gateway
path case, used to follow the primary Cake2 request through G0--G18 and
the G18 resolver boundary. The weather runs serve a different purpose:
they test whether successful tool-using requests keep the same
control-plane shape while recording the deeper \texttt{web\_search}
runtime path.

Cake2 and Weather. The Cake2 artifact is a historical primary audit case
that predates later TraceClaw collector improvements used for the Weather
runs; the score table therefore reports evidence status, not an intrinsic

\subsection{Gateway Path Validation -- Cake2}

The Cake2 request is the primary Gateway-path case. It can be followed
through all G0--G18 stages, not only the early G0--G8 checks. The trace

and normalized, how the Session and Agent are resolved, how duplicate work
is excluded, and where the default resolver is selected.

The point is not that Cake2 is special. Its value is that it is ordinary:
an accepted request still depends on many quiet control decisions. Cake2
shows that the effective Agent comes from Session state, that admission is
the result of several Gateway checks, and that G18 is the place where
control moves toward the deeper Agent Runtime. The archived Cake2 case
does not contain a complete top-level post-G18 \texttt{agentRuntime}

\subsection{Audit Findings from the Ledger}

The ledger produces findings that a final-answer benchmark would miss and
that raw traces do not state on their own. First, Cake2 has complete
source-and-value coverage, but only 16 of 19 stages are directly observed
by runtime or native evidence. The three source-grounded stages are G6
(requested Agent override is absent), G15 (context finalization), and G16
(normal reply-dispatch path). This gives a simple runtime-visibility
baseline: direct runtime/native evidence exposes 16 of 19 Cake2 stage
outcomes, while source anchoring plus concrete case values makes all 19
stages auditable. The gap is not cosmetic; it identifies where the system
currently asks the auditor to trust source reconstruction.

Second, G3 shows an audit-relevant contrast across the saved traces. In
the observed Cake2 path, G3 is reached after device-token fallback and the
request carries an administrator scope. In the Weather runs, shared
authentication succeeds and authorization proceeds through
\texttt{operator.write}. This contrast is useful for audit, but the
current cases do not establish that authentication method alone determines
the resulting scope; client state, Session state, or configuration may
also contribute. Third, G1 records a shared-credential deny in Cake2, but
the connection continues through the device-token path. That is a normal
path in the trace, but it is exactly the kind of fallback that an operator
may want surfaced.

Fourth, G2 records the final authentication pass, but the native trace
does not separately expose the device-token rate-limit state or the exact
pairing sub-branch that made the role and scope check succeed. Finally,
G10, G14, G16, and G18 show rationale-level observability gaps: the final
stage outcome is visible, but some internal branch reason or returned
object fields are not directly emitted. These gaps are direct outputs of
the ledger, not assumptions about the architecture.

\subsection{Current Coverage and Failure Conditions}

The current evidence supports a conservative claim: Cake2 validates the
Gateway path, and Weather validates repeated tool-using runtime behavior
for a small set of successful requests. It does not support broad claims
about every OpenClaw branch. The evaluation still needs rejected requests,
failed tool calls, retries, cancellations, concurrent conflicts, and
cross-version drift.

A trace passes validation only if each required stage has a source anchor
and the selected branch is consistent with the observed values. It fails
if a required stage has no source anchor, if an observed value contradicts
the claimed branch, if a stage is silently skipped without explanation, or
if a claimed post-G18 runtime chain cannot be linked back to the G16/G14
return path. These failure conditions are part of the method, not just
bookkeeping. They make the analysis falsifiable: a trace is not accepted
merely because it is plausible or because it matches a high-level diagram.

\section{Limitations}
\label{sec:limitations}

This paper studies one primary request and six additional successful
weather requests. That is enough to check whether the same control-plane
shape can be preserved across a small set of runs, but it is still not a
coverage result for all Gateway behavior. The Cake2 trace should be read
as a detailed audit case, and the weather traces should be read as
repeated successful executions. They should not be treated as a controlled
comparison of prompt types, because the historical Cake2 artifact predates
later TraceClaw collector changes used by the Weather runs. A stronger
evaluation would rerun Cake2 and Weather under the same OpenClaw commit,
TraceClaw instrumentation commit, trace schema, configuration fingerprint,
and environment, then add rejected, failed, retried, cancelled, and
cross-version requests.

The evidence is also uneven. Some branches are directly observed in the
runtime trace, while others are source-derived because the runtime does
not emit an event for every internal decision. This is not only a
weakness; it is also a useful diagnostic result. The trace shows where
additional instrumentation would make the control path easier to audit.
At the same time, the paper stays focused on gateway and runtime control
flow. It does not evaluate the quality, safety, or factuality of the final
natural-language answer.

Finally, the current presentation is still constrained by the paper
format. The appendix keeps the evidence available, but long source traces
are hard to read in print. The same material would be easier to inspect in
an interactive artifact that links stages to code, values, and runtime
events. Hardware, environment, repository, and release metadata should
also be checked again before submission; the supplementary appendix
records the current state of that information.
